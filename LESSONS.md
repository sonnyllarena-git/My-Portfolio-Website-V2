'w-[340px]' : 'w-14 hover:w-[340px]'`) or close the popup on the ancestor's `onMouseLeave` — don't leave the two states able to disagree. A same-instant screenshot proves the open state renders; it doesn't prove the close/transition path is safe.
- [2026-08-26] Eyeballing a Playwright screenshot to calibrate an invisible click-target's position against a baked-in video/image graphic (`StartupLoadingScreen.jsx`'s Sign-in-button hit area) was off by several percent even when it looked "close enough" in the rendered screenshot — a highlighted overlay box that visually overlapped the real button was still ~2% too wide and shifted down/right of the actual edges → instead of eyeballing, draw the paused `<video>` frame to an offscreen `<canvas>` via `page.evaluate` and scan real pixel RGB values along a horizontal/vertical line through the target (`ctx.getImageData`) to find the exact color-transition boundaries; this is far more precise than a coarse "does it look aligned" screenshot comparison and took one script instead of several rounds of nudge-and-recheck.
- [2026-08-26] `useUnmutedAutoplay.js`'s original fallback for a blocked unmuted `<video autoPlay>` was to leave it fully paused and show a "Click anywhere to continue" prompt — technically correct but means the boot video visibly does nothing until a click, which read as broken/slow. Browsers never block _muted_ autoplay → tried falling back to `video.muted = true; video.play()` immediately instead of leaving it frozen, unmuting on the user's first genuine click. Sonny explicitly rejected this for `StartupLoadingScreen.jsx`: he'd rather the boot video wait silently for a click than ever play without real sound → don't assume "starts instantly but briefly muted" is always the better trade-off than "waits for a click but never muted" — when a video's audio is part of the point (a startup chime here), ask/confirm before defaulting to a muted-autoplay fallback instead of just waiting for a gesture.
- [2026-08-26] Built `ContactModalLayer.jsx`'s `fixed inset-0` modal backdrop assuming it would cover the full browser viewport (matching every other `fixed inset-0` modal in this codebase) — confirmed live via `getComputedStyle`/`getBoundingClientRect` that it was actually clipped to the parent `Window`'s own rectangle. Root cause: `react-rnd` positions each window via a CSS `transform: matrix(...)` on its wrapper (not `left`/`top` as an earlier research pass into `node_modules/react-rnd` had concluded), and any transformed ancestor becomes the containing block for `position: fixed` descendants per the CSS spec → every existing `fixed inset-0` modal in this project that's rendered inside a `Window` (`GameRatingModal.jsx`, `StoreSizeChartModal.jsx`, etc.) is actually already scoped to that window's bounds, not the true viewport — this is the established, correct behavior here (a modal should stay inside its own app's window, not black out the whole desktop), not a bug to fix; just don't assume `fixed inset-0` means "covers the browser" anywhere inside a `Window`, and don't trust a stale claim about `react-rnd`'s positioning mechanism without re-verifying via `getComputedStyle` on the actual live DOM.
- [2026-08-26] Tried to verify a React Three Fiber `<Canvas frameloop="never">` actually stopped rendering while a window was minimized. `requestAnimationFrame` call-counting was unreliable (polluted by an unrelated concurrent session's own R3F canvas also running on the page, plus inherent headless/SwiftShare RAF timing noise) and reading canvas pixels back via `drawImage`+`getImageData` returned all-zero data (WebGL's default `preserveDrawingBuffer: false` means the browser can clear the drawing buffer right after compositing, so an out-of-band script read gets a blank frame) → the reliable way to prove a Three.js/R3F canvas is actually rendering (or not) from outside the app is to monkey-patch `WebGLRenderingContext.prototype.drawArrays`/`drawElements` via `page.addInitScript` (before any context is created), keyed per-canvas via `this.canvas`, and count real draw calls — this cleanly isolated the target canvas from an unrelated concurrent canvas and confirmed 720 draws/sec while open vs. exactly 0 while minimized.
- [2026-08-27] Building the Tech Stack app's falling-keycaps scene (ported from a separate project, `three`/`@react-three/fiber`/`@react-three/drei` re-approved for it), a Playwright `page.screenshot()` of the open window came back completely blank — dark background, zero keycaps — even seconds after the fall should have settled, with zero console/page errors. Nearly concluded the port had a real positioning/rendering bug and started swapping in debug meshes (a plain unlit box, then a giant static box at the world origin) — none of them showed up either. Root cause, same underlying fact as the entry directly above but a different symptom: `page.screenshot()` (not just manual `drawImage`/`getImageData` pixel readback) also comes back blank for a live, correctly-rendering WebGL canvas when `preserveDrawingBuffer` isn't set, because the buffer can be cleared right after compositing, before the screenshot's own capture reads it → temporarily adding `gl={{ preserveDrawingBuffer: true }}` to the `<Canvas>` immediately revealed the scene was working correctly the whole time (keycaps correctly falling, piling, hover/hover-particle effects all functioning). Don't trust a blank `page.screenshot()` of a `<canvas>`-based WebGL/Three.js scene as proof of a rendering bug — add `preserveDrawingBuffer: true` (temporarily, just for the verification pass; it's an unnecessary perf cost to ship) before concluding anything is actually broken, and revert it once screenshots confirm the real behavior.
- [2026-08-28] Reworking the Tech Stack scene from a one-shot fall into a continuous no-gravity float, the whole scene stayed blank for ~1-2 seconds after the window opened, every time, even though the underlying position math was already correct (confirmed via screenshots taken a few seconds later, which showed everything in the right place) → root cause: `@react-three/fiber`'s `<Canvas>` wraps its entire children tree in one Suspense boundary by default (fallback `null`), and drei's `<Text>` suspends on its first-time font fetch (troika-three-text) — so every _other_ mesh in the scene (the keycap boxes, their icon decals, none of which suspend on their own) stayed invisible too, blocked by that one shared boundary, until the font finished loading. Fixed by wrapping just the `<Text>` in its own local `<Suspense fallback={null}>` inside `KeyCap.jsx`, so the boxes/icons render immediately and only the text label pops in a moment later → whenever a scene mixes an async-loading drei component (`Text`, `useGLTF`, `useTexture`, etc.) with synchronous ones under one `<Canvas>`, give the async one its own local `Suspense` boundary — otherwise its load time becomes the whole scene's, and the effect reads as broken/blank-on-open rather than a font just being slow.
- [2026-08-28] The Tech Stack scene originally split keycaps across two overlaid `<Canvas>` elements (a `pointer-events-none` "front" layer purely for visual depth, an interactive "back" layer) — a direct port of the source project's design, where it made sense because those two layers needed to sandwich unrelated page DOM content in z-order. Ported as-is into this app (where the Tech Stack window has no such foreground content to sandwich), it silently made ~60% of keycaps permanently non-interactive by construction, which Sonny caught by trying it live ("not interactive") long before any error would have surfaced it — `npm run verify` has no way to catch "an entire layer's pointer events are structurally disabled." → when porting a multi-canvas/multi-layer visual trick from another codebase, re-derive _why_ the split existed there before assuming it still applies; here a single `<Canvas>` with per-object Z position was both simpler and correct, since three.js's own depth buffer already gives real front/back occlusion without needing two DOM-stacked layers at all.
- [2026-08-28] This project's ESLint config only defines browser globals, not Node's — stubbing `fetch` for a test via `global.fetch = vi.fn()` (Node's ambient `global`) passes at runtime but fails lint with `'global' is not defined (no-undef)` → use `globalThis.fetch` instead, which resolves in both Node and the browser and needs no extra global declaration.
- [2026-08-28] `vite.config.js`'s `test` block has no `globals: true` and no `setupFiles`, so `@testing-library/react`'s automatic per-test `cleanup()` never registers — every prior component test file happened to call `render()` only once, so the leftover DOM from a previous test never caused a collision. The first test file with two `it` blocks that each call `render()` (`RichTextField.test.jsx`) failed with "Found multiple elements with role textbox," because the first test's tree was still mounted when the second ran → any test file that calls `render()` more than once needs its own explicit `import { cleanup } from '@testing-library/react'` + `afterEach(cleanup)` (or the project needs a shared `setupFiles` entry doing this once) — don't assume RTL's auto-cleanup is active just because the package is installed. Same root cause bites `@testing-library/jest-dom` matchers (`toHaveTextContent`, `toBeInTheDocument`, etc.) — the package is installed but never imported anywhere in the existing test suite, so Vitest's Chai has no idea those matchers exist and throws "Invalid Chai property" → without a shared `setupFiles` entry doing `import '@testing-library/jest-dom'` once, stick to plain DOM assertions (`element.textContent`, `element === null`) like every existing test file already does, or add the import locally to a new test file before using any jest-dom matcher.
- [2026-08-29] `ResumeBuilderForm.jsx`'s "Change template" link on the Preview & Download step reused the exact same `handleSelectTemplate` callback the initial step-0 picker uses, which unconditionally calls `goToStep(1)` — so choosing a different template from Preview silently sent the visitor back to Personal Details instead of back to Preview, even though their already-entered data was untouched. Unit tests never caught it (they only ever picked a template once, from a fresh mount); only a live Playwright walk through the full wizard with a template switch surfaced it → any "restart a sub-flow from its entry point" action (here, the template picker) needs to know which step to return to, not hardcode the first-run destination — added a `returnStep` state set to `LAST_STEP` only when entering the picker via "Change template," defaulting to the original first-run step otherwise.
